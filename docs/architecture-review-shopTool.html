Problem：ShopDB 这个 module 是 shallow 的——interface 和 implementation 几乎一样宽，且 getDB() 是工厂不是单例，每条 webview 消息都重铸 ~59 条 prepared 语句（`index.ts:162`），接口没隐藏任何东西。

  • 深度：接口收缩，SQL 与一致性收进实现
  • leverage：prepare 一次，N 条消息零重建
  • 删 3 个死方法 + 悬挂缓存半边（含 Phase 4 引入但未接线的死代码）
  • 测试可以廉价开内存库 → 是候选④的铺路石

  • 测试只需普通对象，无需 vscode/sqlite
  • net() 一个函数收编六处重算
  • deletion test 通过：闭包变纯函数

Problem：所有 client-*.js 在同一个顶层作用域声明 var/function，“谁定义、谁调用”只能靠文件头的「加载顺序第 N 个」注释 + grep 反推；加载顺序本身是三处手抄契约（index.ts 数组、头注释、webview loader）。

Solution：每个文件显式 declare 自己导出的符号（小型注册表 sel.register({...})），入口 main.js 只负责 init/wire 一次，契约收敛成一张表。

  • AI 可导航：依赖图一眼可查
  • 契约从三处手抄变一张注册表
  • 成本：动 6 个文件 + loader，纯 JS 无 bundler 约束

先做 ① —— 一次性预编译 + 修剪 DB interface

最小的低风险一步：给 DB module 一次编译/缓存，并清掉死幅面（含 Phase 4 遗留死代码），为 ④ 的纯 seam 测试铺路（廉价内存库 → 直接测钱规则）。② 可紧随其后共享同一次重构窗口。汇报详见候选卡。
