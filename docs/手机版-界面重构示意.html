为什么这样扩展性强

现在加一个功能 = 往顶栏塞一个按钮（塞到第 4 个就挤）。重排之后，加东西有三个现成的位置，按"这个东西有多重"选：

位置放什么以后可能放的
底部 tab
（换大模块）		一个独立的功能区，整页切走销售记账、月度盈亏（现在是电脑版独占）
内容区小 tab
（同一批数据的看法）		换个方式看同一批商品只看星标、只看套装、按品类分组

顶部工具行跟"找东西"直接相关基本不用再动

分页条（这次补画的）

原来这张图漏了它 —— 而它是现成的功能：现在画册和列表底下共用一条 « | ‹ 上一页 | 跳页下拉 | 第 1–50 条 · 共 348 条 · 1/7 页 | 下一页 › | »。

位置不动：还是内容区正下方、底部 tab 之上，画册/列表共用同一条（切 tab 不重画、不换位置）。
只把一排六个控件收敛成三个：‹ 上一页 · 1/7 页 · 下一页 ›， 点中间那颗「1/7 页」弹出页列表跳页（手机上本来就用下拉跳页，不用数字键盘）。

⚠️ 代价说清楚：« / »（第一页 / 最后一页）和那个独立的下拉撤掉了 —— 功能没丢（跳页还在，只是收进中间那颗），但「一键跳到末页」要多点一下。这是刻意换来的宽度（300px 一排挤六个控件太密）。 页数少（≤1 页）时整条可以收起来。

「348 条」没跟着下移，还留在小 tab 那一行最右边：分页条精简之后已经不写条数了， 总数总得有个地方说 —— 于是小 tab 行右边是总数（348 条）、分页条中间是第几页/共几页（1/7 页），各说一件事不重复。

两处位置的挪动

① 那行 348 条 原来挤在搜索框右边，挪到小 tab 那一行的最右边（它说的是"现在显示多少条"，跟内容区更近）。
② 分页条本身不挪窝，但控件从六个收到三个（见上）。

这次一个功能都不会丢：搜索那行的"搜哪一列"下拉（全部/编号/名称/品类/系列）和漏斗筛选按钮原样保留（漏斗上的小数字＝生效中的条件数，跟现在一样）；画册/列表变成内容区的小 tab；设置从顶栏挪到底部 tab（日志并进去当第三个页签）；「🔄 有改动」变成底部「设置」格上的小红点；连接指示灯缩成底部右侧一个小圆点。

代价说清楚：这是重构手机版的框架，动的是 src/webview/mobile/index.html 的骨架和 app.js 里跟显隐/切换有关的那部分 —— 比套装那个功能的风险大，因为所有页面的外壳都过一遍。建议先定设计，再分批改（可以一个 tab 一个 tab 地搬）。

实施记录 · 第 1 批「外壳」（2026-10-12 已完成）

改了 src/webview/mobile/ 的 index.html / style.css / app.js，并给 scripts/check-mobile-wiring.cjs 加了一道外壳闸门（--tabbar 的出处、日志页签补画、 旧壳的六个 id 不许回来、抽屉让位）。后端零改动。跟这张图有几处不一样，都是实施时才发现必须这么定的：

图上画的实际做成为什么
顶栏 ＋ 是正方形图标 照样是 ＋，不再写「＋ 新建」 合并成一行后要塞下「搜哪一列 + 搜索框 + 漏斗 + 新建」四样；那两个字在 360px 屏上正好是溢出的几像素
设置页右上角有个「清空」 没做 原来就没有"清空日志"这个功能，属于新功能；要的话单独说一声（已撤的浮层上也只有一个「关闭」）
设置页没有返回箭头 照做：撤掉 #btnSetBack，返回靠底部「商品」格 底部 tab 已经承担了返回；顶上再放一个"返回"和底部「商品」是同一个动作
小 tab 右边写「348 条」 仍是「筛出来的 / 一共多少条」（如 12 / 348） 现有的 #count 本来就是"现在显示多少条"，只挪了位置没改口径。要换成"只写总数"再说
分页条收成三控件 已做（第 2 批），见下面那张表 六控件 → ‹ 上一页 · 1/7 页 · 下一页 ›，中间那颗点开可跳页
小红点在「设置」格上 照做，但它是纯提示、不是按钮 ⚠️ 这意味着底部那个「🔄 有改动」的一键重读没了：自动刷新照旧，手动重读走「设置 → 系统配置 → 🔄 重新从数据库读一遍」。 要是觉得列表页少了个"点一下就刷"的入口，说一声 —— 可以让「点当前那个 tab」= 重读
图里头每台手机底部各有一条 实际是全局一条（四个屏共用，跟着 fixed 在底部） 跟原来那条 #status 细条一个位置；每屏各画一条会有四份状态要同步

第 2 批（分页条）已做完（见下），第 3 批（细节收尾）、第 4 批（搜索行统一下拉）、 第 5 批（详情页返回键）见最后几节。 验收步骤见 docs/手工测试清单.md：外壳看「3b. 外壳三层」（3b.1 ~ 3b.15）、 分页条看「3c. 分页条收成三控件」（3c.1 ~ 3c.8）、搜索行换控件看「3.1c」。

实施记录 · 第 2 批「分页条」（2026-10-12 已完成）

只动了 index.html 里 .pager 那一段 + app.js 的 renderPager() 和三个翻页按钮的绑定 + style.css 的分页条样式。后端零改动。

图上画的实际做成为什么
点中间的「1/7 页」弹出页列表 用的是原来的跳页下拉（#pageJump），只是外观改成胶囊、选项文字写成「N/M 页」 这样"收起时看到的那行字"和"点开后的列表"是同一份东西，不用另做一个浮层； 手机上弹的就是系统自带的页列表（本来就用它跳页，不用数字键盘）。代价：列表里每一项写的是 「3/7 页」，比图上的「第 3 页」多带了个总页数
胶囊文字 12.5px 16px（跟其它下拉一样） ⚠️ iOS 上聚焦 font-size < 16px 的输入框/下拉会把整页放大， 放大之后就很难缩回来（我们还专门拦了系统手势）。这条是硬约束，不是审美
中间那颗一直显示 ≤1 页时整条分页条收起（#pager.hidden） 只有一页还摆"上一页/下一页"是干扰。⚠️ .pager 自己是 display:flex， 必须配一条 .pager[hidden]{display:none}，否则 hidden 盖不住它（check:mobile 第 ⑦ 道闸门钉着）
图上没提「第 12–50 条」 整串条数不写在这儿了 内容区顶上那一排小 tab 的右边已经有「筛出来的 / 一共多少条」，同一件事写两遍像两个数。 总数没丢：鼠标停在胶囊上会提示「共 348 条 · 第 1/7 页」

实施记录 · 第 3 批「收尾」（2026-10-12 已完成）

第 2 批做完、上手机看了一遍之后的两处反馈。只动 src/webview/mobile/ 三个文件 + 闸门 scripts/check-mobile-wiring.cjs，后端零改动。

反馈改成了什么为什么
日志那边没有清空 「设置 → 日志」的标题行右边加了一个「清空」按钮（#btnClearLog， 复用现成的 .listhead 排法），点了就把这一页清干净 + 弹一句「日志已清空」 清的是本机这一份展示副本（state.logs，内存里，最多 300 条）—— 服务端那台机器上的日志文件不动、别人那台手机也不受影响。纯展示的东西，不弹确认框： 清错了再操作一次就又有了，为这点事拦一道不值
清空之后列表一片白 renderLogs() 里加了个空态：没有日志时显示一行灰字 「（现在是空的。之后的操作会一条条记在这儿）」 一片白看着像页面坏了，人会以为按钮把日志页点死了；一行灰字说清"是真没有"，才敢接着用
中间那颗「1/11 页」跟上一页下一页不自然 .pager select.pj 从品牌绿胶囊（绿字 + 9% 绿底 + 绿描边）改成 并进两侧那一套：底色 --soft、描边 --line、同 36px 高； 仍然保留两处标记 —— 圆角 999px 的胶囊（两侧是 8px 方角）+ 文字品牌绿加粗 原来那版整块绿底，实机上看它成了整条最抢眼的一坨，两侧按钮反倒像配角，一排三个不像一家人。 现在一排三个是同一套浅底 + 细描边，唯一那点彩色留给"当前在第几页"。 ⚠️ 字号仍是 16px，不许改小（iOS 聚焦 <16px 的下拉会把整页放大）

实施记录 · 第 4 批「搜索行统一下拉」（2026-10-12 已完成）

商家反馈：「上方那个搜索还是统一比较好，就是类别那边不要做成圆圈，圆圈还是直接用筛选那边的功能吧， 搜索那边统一下拉吧」。只动 src/webview/mobile/ 三个文件 + 闸门 + 文档，后端零改动。

这是在补齐一个早就定过的口径：电脑端当年就把「状态 / 品类 / 等级」统一做成了下拉 （client-product.js 的 KW_SELECT_SCOPES，那行注释写着「商家明确说过不喜欢圆圈圈」）， 手机版只把「状态」做了，品类/等级两列漏下来还是圆片 —— 所以同一件事两边长相不一样。

原来的样子改成了什么为什么
搜索行里两套控件：#scopeStatus 下拉（状态）+ #scopeChips 一排圆片（品类/等级） 合并成一个 #scopeValue 下拉，选项按当前列重建 （「全部状态 / 在售 / 已下架」、「全部品类 / 个护（12）/ 香薰（7）…」） 这三列本来就是同一类「取值封闭、选比手打准」的列，没必要一列一个控件。 电脑端就是一个 #keywordSelect，口径对齐
圆片能多选 下拉只能单选；要多选回筛选面板勾 —— 圆圈只留在面板里 商家原话「圆圈还是直接用筛选那边的功能吧」：面板的活是"勾一批"，搜索行的活是"点一个"。 面板里勾多个时这个下拉只显示第一个，但条件一条不少（顶部胶囊上都写着）
圆片上带着「这一类有多少个」 数字挪进下拉选项：个护（12） 那个数是全量统计，看"库里还剩几种"挺有用 —— 换控件别顺手把它弄丢
「品类为空」那一档在圆片上勾得到 下拉里不放（它会和"全部"撞同一个空串 value，变成永远选不中的死选项）；要筛它去面板勾 空串和"全部"只能二选一；面板那条路还通着，能力没丢

实施记录 · 第 5 批「详情页返回键」（2026-10-12 已完成）

商家反馈：「点套装 → 进套装详情 → 又点子商品，之前上一步是返回套装，我感觉不需要这样， 直接上面的 < 就是返回商品主页，不需要返回上一步的操作」。 只动 src/webview/mobile/ 三个文件 + 闸门 + 文档，后端零改动。

这同样是补齐电脑端早就定下的口径：docs/套装-使用说明.md 里明明白白写着桌面端 「没有"返回上一步"按钮，别找 —— 想回套装就点子商品底下的「属于 …」里的编号」。手机版当年多做了一套 来路栈，反而和电脑端不一样。

原来的样子改成了什么为什么
详情页那个 < 商品 会变：从套装点进子商品后，它变成 < T001，点一下退回那个套装（有一套 detailBack 来路栈在记） 删掉来路栈（detailBack / updateBackLabel / pushBack 一起删）。 那个 < 永远是「回商品列表」，文字固定「商品」、不再变 套装和子商品能互相点（A→B→A→B…），堆几层之后用户根本不知道这一下会退到哪儿； 还有"得连着按十来下才回得到列表"的观感。回列表本身就该是一步到位的事
想回套装只能靠那个会变的返回键 回套装走子商品页顶部那行「属于：T001」（编号胶囊，点了跳过去） 那个入口本来就在、且是"我在哪个套装里"唯一说得清的地方；返回键只剩一个含义，两边都不打架
