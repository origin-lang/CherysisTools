## 一、为什么做这份存档

- 方案 A（共享文件夹）已实装加固并交付团队使用；多人场景真实存在但「**通常一人主录、偶尔两人并发写**」。
- 调研确认：B 的接缝只有一条——`handleMessage`，**前端零改动**即可支持「主机 / 客机」两种角色。
- 用户反馈：HTTP 方案自己没用过、最初不敢用；听完利弊后决定「A 收尾 OK，重心转为给 B 铺路」。

## 二、决策记录（访谈定稿）

1. **起步**：方案 A 维持现状（已实装），B 作为「铺路」对象；不做 B 以外的额外架构（不做实时推送、不做版本号冲突检测）。
2. **主机形态**：主机 = **开 VS Code 的任意团队成员**（复用全部后端代码，无需独立进程）；换主机 = 谁开谁当。
3. **数据库归属**：库**仍放共享文件夹**（单一副本），主机只是「代读写」的临时大脑 → 换主机**零数据迁移**。
4. **防双主**：同一时刻只能一台主机；主机启动时在共享 storageDir 写锁文件（`.shop-host.lock`，含主机名/时间戳）+ 间隔探活，别人再开则提示「已有主机」。
5. **客机**：前端不变；`handleMessage` 转发到主机；**不初始化本地库**；受限操作提示「请在主机上操作」。
6. **安全 MVP**：不加认证（局域网信任），主机启动时打印端口地址；将来可加令牌鉴权。
7. **明确不做（NO）**：冲突检测（覆盖有提示）、实时推送、导出文件回传客机（将来按需加下载端点）。

## 三、架构事实（调研结论，已核对代码）

- 前端唯一通道：`vscode.postMessage({type, ...})` → `index.ts` 的 `handleMessage(msg, ctx)`（`src/tools/shopTool/index.ts:161`）；回推走 `ctx.postToWebview` / `ctx.log`（`src/core/toolContext.ts`）。
- **接缝点**：`handleMessage` + 已有的 `h`（`HandlerCtx`，`index.ts:440`）中间层——本地执行 / 转发在这个位置切换。
- 后端对 VS Code 的耦合（**必须留在「你眼前这台机器」上执行**，转发会弹错屏幕或失去意义）：
  - `revealFileInOS`：`handlers/live.ts:243/334/351`、`handlers/image.ts:274`、`handlers/impexp.ts:389`
  - 系统对话框 `h.ctx.selectFolder / selectFile / selectFiles / confirm`（`toolContext.ts:22-24`）
- **图片查看**：封面 / lightbox 已走 base64 按需下发 → 客机无需本地图片目录也能看图。
- **撤销 / 重做栈**在主机内存 → B 落地后「撤销统一、跨机不互相覆盖」自动成立，方案 A 的头号坑被 B 结构性消解。
- 客机面板应跳过 `resourceRoots` 图片资源注入（本地无可指向目录）。

## 四、协议草案

- 主机：`POST /api/shop/invoke`，body `{ type, payload }` → 执行对应 handler → 回 `{ ok, posts: [...], logs: [...] }`（捕获本次请求期间的回推消息与日志，由客机重放到自己的 webview）。
- 主机：`GET /api/shop/ping` → `{ ok, host, up }`（客机做断连检测 / 换主机提示）。
- 实现用 Node 内置 `http` 模块（**零新依赖**），端口固定 13800（计划做成可设置）。
- 后 opcode：将来若要文件回传，加 `GET /api/shop/file/{token}`。

## 五、受限操作清单（MVP）

客机不开放（会提示「请在主机上操作」）：
- 导入 CSV / 数据库恢复备份
- 批量导图 / 图片目录相关（改 `image_dir`）
- 导出落本地文件（Excel / 图片导出等文件会落在**主机**的配置目录）

客机正常使用（全部走转发）：查看全表 / 录销售 / 改库存 / 上下架 / 星标与直播排品 / 查规则 / 撤销重做。
