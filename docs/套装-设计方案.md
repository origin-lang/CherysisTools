# 套装（T 编号）—— 设计方案

> 状态：**设计稿 v1，2026-10-11 与商家逐条确认完毕，尚未实现**。
> 本文只谈"怎么做"；面向使用者的操作说明见 [套装-使用说明.md](套装-使用说明.md)；界面示意见 [套装-界面示意.html](套装-界面示意.html)。
>
> **一句话**：套装是一个**只卖不存**的商品 —— 一张合影图打包卖出去，它的"内容"是若干个普通商品的编号，自己不记库存、不管销量。

---

## 一、为什么这么做（背景）

珠宝店里"一套"是常见的卖法：一条项链 + 一对耳环 + 一个手链，拍一张合影图挂出去卖。它跟单品有三个本质区别：

1. **它没有自己的库存** —— 能不能卖出去取决于里面那几个单品还剩多少，但这套逻辑商家现在不用（库存/销量功能尚未启用）。
2. **它的成本不是采购来的** —— 是零件的成本之和。
3. **它和单品是"多对多"关系** —— 同一对耳环可以出现在"婚礼套装"和"日常套装"里。

因此它不是"另一种商品表"，而是**商品的一种用法**（见决策 1）。

---

## 二、已敲定的决策

每条都记了理由 —— 理由比结论重要，因为将来想改的时候，得先看理由还成不成立。

### 决策 1：套装与普通商品**共用 `products` 表**，不单开表

**理由**：套装要能被搜到、要有图、要能看详情、要能进九宫格和直播排品 —— 这些能力 `products` 全有。单开一张表等于把这些能力再写一遍，而且是永久的双份维护（每次改列表/详情/筛选都要问"套装那边同步吗"）。

**代价**：套装会混在商品列表里（靠筛选区分，见决策 8），以及删除功能时要扫一遍接入点（见第六章）。

**"以后不好删"这个担心已经用三重隔离解决**：约定隔离（`T` 前缀）+ 代码隔离（集中在一个模块）+ 数据隔离（`set_items` 独立表）。真不要了：关开关 → 入口消失；再删表删列 → 数据清空。

### 决策 2：加一列 `kind`（`0` 普通 / `1` 套装），**不能只靠 T 前缀**

**理由**：编号和类型是两个维度。改号是允许改前缀的（`A001 → L001` 合法），所以只用前缀判断会有两种坏情况：

- 把 `T001` 改成 `A001` → 这个套装**凭空变成普通商品**，而且是"改号顺带改类型"这种极难察觉的副作用（改号还会连带改图片夹，本来就是个重操作）。
- 新建时手滑输了 `T005` 当普通商品 → 系统照单全收，它看起来是套装。

前缀给人看（一眼认出来），`kind` 给机器判断。两者互为冗余 —— 冗余在这里是好事：约定被破坏时机器仍然知道真相。

**代码里只允许一处定义** `SET_PREFIX = "T"`，不许各处散着写 `startsWith("T")`。

### 决策 3：禁止**跨类型改号**

`T001` 只能改成 `T` 开头的编号，普通商品不能改成 `T` 开头。理由：改号会连带重命名图片文件夹，一旦跨类型还顺带改了身份，事后无法追查。不许跨类型，前缀和 `kind` 就永远不会打架。

（另一个做法是"改号时同步翻转 kind"，但那等于"改个编号就把商品变成套装"，更危险，不采纳。）

### 决策 4：套装与子商品是**多对多**

中间表 `set_items`。理由：同一副耳环进多个套装是常态，多对一以后必然要改数据模型，那时迁移成本高得多。

### 决策 5：**进价自动汇总（不可手填），售价手填**

- 套装的 `cost_price` 不是一个"值"，而是**派生值**：子商品进价之和。它**不落库**（落库就一定会跟子商品的真实进价不同步 —— 这是这类系统的经典坑）。
- 套装的 `sale_price` **手填**：打包让利多少是生意判断，机器算不准。
- 复用现有 `price_manual` 列，套装恒为 `1`（含义：别按等级规则自动覆盖我填的价）。
- 详情页显示"子商品合计售价"作参考，以及**差额**（让了多少 / 贵了多少）。

### 决策 6：**不记库存、不管销量**；销量与库存归子商品

套装不显示库存（不是"显示 0"，是**这一格不存在**）。销量/收入的口径是"算到子商品头上" —— 但这两个功能商家目前都还没启用，所以**先留白，不写任何统计代码**。将来真做的时候方向已定：按子商品算。

### 决策 7：套装**没有等级**（等级那一格隐藏）

等级的作用是驱动 `sale_rules` 自动算价（`cost*1.5` 之类）。套装售价手填（`price_manual=1`），等级已经不参与算价，留着只会让人困惑该填哪个。

### 决策 8：**不单开视图**，"只看套装"走筛选

曾考虑在列表页加第三档视图（画册 / 列表 / 套装），结论是不加。因为**套装在语义上属于画册**（它也是"有图的东西"），套装卡片跟画册卡片几乎一样（只多一个角标和一行"含 N 件"）。给它单开一档，本质是**把"筛选"伪装成"视图"** —— 以后再想加"只看在售"是不是又要开一档？档位会越来越长。

所以：**画册档里套装照常出现**（带「套」角标），**"只看套装"做成筛选面板里的一个开关**。

### 决策 9：导入**不做**套装，导出**带**"组成"列

`set_items` 是**关系**，不是字段。导入表是"一行一个商品、一列一个字段"，把关系塞进字段列会让语义变脏（商家原话："这个组成不是字段吧，不是字段加进来不好吧"）。

- **导入**：不处理套装（要额外解析 + 处理"编号不存在/格式错"，容易犯错，代价是污染数据）。套装手工搭。
- **导出**：带一列"组成"（如 `A001,A003,L004`），**纯只读参考**，用来核对。写错了没代价。

### 决策 10：导入时**拒绝** `T` 开头的行

既然导入不管套装，那就必须堵住"表里出现 `T001`"这个洞：否则它会以"看着像套装、其实是普通商品"的样子躺在画册里，破坏决策 3 的约定。**拒绝并提示"T 开头的编号请手工建套装"**。

### 决策 11：从套装里移出一个商品 —— 手机左滑、电脑右键

两边的既有习惯不同，不该互相迁就：

| 端 | 触发 |
|---|---|
| 手机网页 | 行上左滑，露出「移出」按钮 |
| VS Code 面板 | 右键菜单 →「从套装移出」（复用现有右键机制 `client-product.js:620`） |

**同一个后端动作，两种触发方式**。注意：**左滑/右键移出的是"关联"**（这个商品不再属于这个套装），**不是删除商品** —— 商品还在、还有图、还在列表里。

> ### 🔄 2026-10-11 三改：清单拆成「浏览态 / 编辑态」（**推翻**上表"手机直接左滑"那半）
>
> 手机版实测报出两条：① 电脑（鼠标/触控板）**没有左滑手势**，那个藏在行底下的「移出」等于**没有入口**（我一度的修法是"常驻显示"，商家看过嫌丑，作废）；② 浏览清单时**一点整行就窜进子商品详情**，误触太多。
>
> 定案：清单分**浏览态 / 编辑态**，靠右上角一个「**编辑 / 取消编辑**」按钮切换 ——
>
> | 操作 | 浏览态（默认） | 编辑态 |
> |---|---|---|
> | 点**编号** | 进子商品详情 | 无效 |
> | 点行内其它地方 | 无效 | 无效 |
> | 左滑一行（手机） | 无 | 露出「移出」 |
> | 右键一行（电脑） | 无（只挡掉浏览器原生菜单） | 菜单 →「移出 编号」 |
> | 添加子商品 | 收起 | 下面露出输入框 |
>
> 几条要点（都在代码里留了注释）：
> - **进详情只认"点编号"** —— 跟列表视图"只有编号列带 `data-open`"是同一个规矩，不再整行可点。
> - **一个 `.editing` class 管三件事**（添加区显示 / 左滑能不能跑 / 行点击认不认）。别在别处再各记一个状态位，否则会出现"能左滑但不能加"这种半吊子状态。
> - **电脑端移出只走右键**，编辑态里也**不给**「移出」按钮（撤掉了原来那套"常驻显示"）。
> - **右键也只在编辑态出**（A 方案，商家改定的）—— 跟手机端一致：手机也是进了编辑态才左滑得出「移出」。
>   "能不能操作"的判据因此**只有 `isEditing()` 一条**。浏览态右键只是把浏览器原生菜单挡掉、不出东西
>   （不挡的话，Web App 里右键会弹出"另存为 / 查看源代码"，比没反应还怪）。
>   > 一度选过 B（浏览态也能右键），但那样菜单里得放「添加子商品」，而它只能靠"**顺手把卡切进编辑态**"
>   > 来兑现 —— 等于"不声明就改状态"，正好跟这条规矩相反。A 把菜单收成**只有「移出」一项**，反而更短。
> - 右键菜单项**只有「移出 编号」**（编辑态下面本来就有添加框，右键再给"添加"是重复）。⚠️ 触屏长按也会触发 `contextmenu`，所以用 `matchMedia("(hover: hover) and (pointer: fine)")` 只放行**有鼠标**的设备。
> - 切进编辑态**不自动 focus 输入框**：编辑态同时服务"移出"和"添加"，为移出而来的人不该被弹出来的键盘怼一脸。
>
> ⚠️ 这一套**只管手机版**。VS Code 面板（详情抽屉）没有浏览/编辑态：抽屉本身就是编辑面，
> 添加框常驻、移出只走右键（见 5.2 那节的说明）。别把 `.editing` 那套往桌面端搬。

### 决策 12：套装编辑**实时存**，但"移出"要确认一次

全站既有规矩是"失焦即存 / 点了立刻生效"，套装不破例（否则会出现"改完忘了点保存 → 白改"）。但**移出**会给一次确认（"把 A003 从 T001 移出？"），因为移出不是高频动作，代价却是"套装少了个零件"这种不易察觉的错。

暂不做"撤销"提示（要保存上一次状态，属于给自己加负担的活）。

### 决策 13：**不许套装套套装**

`T` 里不能装 `T`。理由有二：一是循环引用（T001 含 T002、T002 又含 T001 → 合计进价算到死循环）；二是业务上"套装的套装"没意义，真需要就是个大套装，把子商品列全即可。

### 决策 14：九宫格与直播排品**照常处理套装**

它就是个商品，同表天然支持，不需要专门写代码，也不需要专门排除。真出问题再说 —— 符合"别扩散"。

## 三、数据模型

### 3.1 `products` 加一列

```sql
kind INTEGER NOT NULL DEFAULT 0   -- 0 普通商品 / 1 套装
```

用**数字**而不是布尔，将来要加第三种（材料包、赠品）不用再动结构。

**老库升级**：`db.ts:350` 已经有现成的迁移通道（`PRAGMA table_info` → `ALTER TABLE ADD COLUMN`），照抄即可，老数据自动填 `0`。**不需要手工升级、不需要改库版本号**。

### 3.2 新表 `set_items`

```sql
CREATE TABLE IF NOT EXISTS set_items (
  set_code   TEXT NOT NULL,   -- 套装编号，如 T001
  child_code TEXT NOT NULL,   -- 子商品编号，如 A003
  sort       INTEGER NOT NULL DEFAULT 0,  -- 清单里的展示顺序（主推的排前面）
  PRIMARY KEY (set_code, child_code)
);
CREATE INDEX IF NOT EXISTS idx_set_items_child ON set_items(child_code);
```

**为什么存编号而不是 `products.id`**：

- 跟现有 `live_star` / `live_plan` 一致（那两张表也用 `code`）。
- 编号是这套系统的锚点（图片夹名、导入锚点），**改号本来就有连带逻辑**（`renameImageFolder`），把 `set_items` 的更新挂在那条链上很自然。
- 主键 `(set_code, child_code)` 天然防重复：同一个商品在一个套装里只能出现一次。

### 3.3 派生值 —— **一律不落库，实时算**

| 派生值 | 算法 |
|---|---|
| `含 N 件` | `COUNT(*)` |
| `合计进价` | `SUM(子商品.cost_price)` |
| `合计售价` | `SUM(子商品.sale_price)` |
| `差额` | `套装.sale_price − 合计售价`（正数=比拆开买还贵，负数=让利） |

一个 SQL 带 `JOIN products ON set_items.child_code = products.code` 就出来了。

### 3.4 生命周期：改号、删除、导入的连带

这三处是这个功能最容易漏的地方，逐个写清。

**① 改号**（`handlers/product.ts:441` 一带）

改号现在已经有连带动作：`h.renameImageFolder(oldCode, code)`（`product.ts:454`，三档护栏：目标空→拆壳再挪 / 目标非空→取消本次改号 / 改名失败→取消）。套装要加两件事：

- **禁止跨类型**（决策 3）：`canonicalCode` 之后校验"新旧前缀是否同为 T / 同为非 T"，不同就拒绝并提示。
- **改号成功后，更新 `set_items`**：
  - 如果改的是**套装** → `UPDATE set_items SET set_code = 新 WHERE set_code = 旧`
  - 如果改的是**子商品** → `UPDATE set_items SET child_code = 新 WHERE child_code = 旧`
  - 与图片夹改名**同一个事务**（`renameImageFolder` 失败就不该改关联）。

> ⚠️ `canonicalCode` 有**两份实现**：`src/tools/shopTool/pricing.ts:21`（后端权威）和 `src/webview/mobile/client-core.js:243`（前端预校验，避免白跑一趟）。跨类型校验**两边都要加**，口径一致。

**② 删除**（`db.ts:650`）

`deleteProduct` 里已经有一个现成的范本 —— 它已经在清理关联表了：

```js
const tx = c.transaction(() => {
  productSalesDel.run(id);
  productStockDel.run(id);
  pDelete.run(id);
  if (code) {
    liveStarDelByCode.run(code);
    livePlanDelByCode.run(code);
  }
});
```

照抄：同一个事务里再加两条 ——

```js
setItemsDelBySet.run(code);    // 它作为套装被删 → 整个清单没了
setItemsDelByChild.run(code);  // 它作为子商品被删 → 从所有套装里摘掉
```

**删之前要把话说清楚**（决策 11 的配套）：删除确认框里列出"它还挂在 T001、T002 里，会一并移出"。硬删除不可逆，必须让用户在动手前看见代价。

**③ 导入**（`rowParse.ts` / `handlers/product.ts`）

- 遇到 `T` 开头的编号行 → **拒绝该行**，日志里说明"T 开头的编号请手工建套装"（决策 10）。
- 导出：多一列"组成"，`GROUP_CONCAT(child_code)` 按 `sort` 拼，只读（决策 9）。

## 四、后端接口

新增一个 `handlers/sets.ts`（套装逻辑集中在这里，见第六章），注册到 `toolRegistry` 的消息表里。

| 消息 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `setMembers` | `{ code }` | `{ items: [{code,name,cost,sale,status,cover}], sumCost, sumSale, count }` | 套装详情页的主数据 |
| `setAddMember` | `{ code, childCode }` | `{ ok, items }` | 校验：目标必须存在 / 不能是自己 / 不能是套装 / 不能重复 |
| `setRemoveMember` | `{ code, childCode }` | `{ ok, items }` | 移出关联（不删商品） |
| `setOfCode` | `{ code }` | `{ sets: ["T001","T002"] }` | 子商品详情页显示"属于哪些套装" |

写入路径统一走 `db.ts` 的新接口（`listSetMembers` / `addSetMember` / `removeSetMember` / `setsOfCode`），SQL 全部集中在 `db.ts`，跟现有 5 处 `FROM products` 保持同一个风格。

**校验清单**（每个都返回明确的中文错误，不要静默失败）：

- 子商品编号不存在 → "没有 A003 这个编号"
- 目标是套装（`kind=1`）→ "套装不能放进套装里"
- 自己放自己 → "不能把自己放进自己"
- 重复添加 → 幂等处理（不报错，直接返回当前清单）

### 5.1 手机网页（`src/webview/mobile/`）

| 位置 | 改动 |
|---|---|

#### 套装详情页的三个页签（2026-10-11 改定，**推翻**了原先「套装不加页签」那条）

| 页签 | 装什么 |
|---|---|
| 基本信息 | 名称 · 品类 · 系列 **＋ 子商品清单**（「子商品 · N 件」+「编辑」+ 每一行） |
| 价格库存 | 状态 · 售价 **＋ 合计区**（合计进价 / 合计售价 / 比合计） |
| 备注说明 | 备注 |

默认落在**基本信息**，与普通商品完全一致（不记"上次停在哪个页签"，也不给套装做特例）。

**为什么改**：原方案的理由是"套装就名称/售价/备注三个字段，一屏到底反而少点一次"。但落地之后发现，
合计区只能挂在表单最后 → 实际顺序成了 名称 → **售价** → **备注** → **合计/比合计** → 清单，
而 `比合计 = 售价 − 合计售价` 这两个数**天生要并排看**（商家定价本来就是看着子商品每件多少钱凑出一个打包价）。
"一屏到底"把最该相邻的两个数推远了，是**负收益**。分页签后售价正下方就是合计，定价这一趟不用来回滚。

**代价也记清楚**：进套装第一眼是"名称 + 子商品清单"，要改价得点一次「价格库存」。
（所以**默认页不做套装特例** —— 否则手机版和电脑端都要各记一套"第一页是哪页"。）

#### 5.2.1 抽屉的视觉规矩（2026-10-11 改版）

起因：商家说抽屉"**又丑又伤眼睛**"、"都是一个色调看不直观"、"12345 看着头疼"。病根有三条，
都在 `fragment.html`：

| 病根 | 改成 |
|---|---|
| 抽屉里的字号**全是写死的**（10/11/12/13px），而 `--table-font-size` 只挂在 `.data-table` 上 → 调大「字号」设置，列表变大、抽屉原地不动 | 抽屉根上定义 `--d-fs: var(--table-font-size, 13px)`，再派生出 `--d-fs-tag`（−1px，不小于 11px）/ `--d-fs-mid`（+2px）/ `--d-fs-big`（+5px）；**抽屉 CSS 里不许再出现写死的 px 字号** |
| 一切都是同一号灰字、靠一条细线分区 → 没有层级 | 分区卡片化：`.d-form` / `.d-set` 给浅底圆角（走 `--vscode-textBlockQuote-background`）；分区标题**去掉序号**（改叫「商品档案 / 价格与销售 / 状态与辅助 / 子商品」）；字段值用 `--d-fs`、标签用 `--d-fs-tag` |
| **标题**当时是 11px + `descriptionForeground` —— **跟字段标签同一个字号同一个颜色**，商家反馈"感觉黑白色一样"（主题 Light Modern 下卡片 `#f3f3f3`、标题和标签都是 `#717171`，确实灰上加灰） | 标题改成：`--d-fs`（回到正文大小）+ `font-weight: 600` + `var(--vscode-foreground)`（正文色，不发灰）+ **左侧 3px 品牌绿竖标**（`#23a884`，与售价/合计同一个色 = 整页唯一的颜色锚点） |
| 关键数字（售价、合计）跟普通字段一样大，且合计埋在 body 最后 | 售价升到 `--d-fs-big` + `#23a884` + 600 权重；**合计条从 body 挪进头部**（就贴在售价下、底色 `rgba(35,168,132,.12)`）——`比合计 = 售价 − 合计售价`，这两个数必须挨着看 |
| 抽屉 370px 太挤，一列放不下 | **440px**（与手机版宽屏抽屉 `--drawer` 同宽，两边手感一致） |
| 套装把"生来就没有"的字段也画出来，满屏 `—` | `DRAWER_SET_HIDE = {grade, cost_price, stockTotal, soldTotal, netTotal, purchase_link}`：**判据是"这个字段属于套装吗"，不是"这个字段是派生只读吗"**（早先按 `isSetFrozenCell` 写，方向和字段集都对不上） |
| 子商品行**只能右键**，点编号没反应（桌面端一直漏做；手机版早就"点编号进详情"） | 行上挂 `data-open-child`，**点编号** → `openProductDrawer(那个商品)`。**点的地方只有编号**（`data-open-child` 只挂在 `.d-set-code` 上）—— "点整行就窜走"手机版那轮专门否掉过，别在这里破例；⚠️ 断言要同时钉住"编号有点击"**和**"行本体没有 onclick" |
| 桌面端抽屉**没有返回栈**（手机版有 `detailBack`） | 商家定的是 **B 方案：点过去、不管返回**（关掉重开）。不是死路：子商品自己的抽屉底部有「属于」那一行，点套装编号就回来了 |

> 普通商品**同步改**（同一套字号/卡片/头部版式），唯一差别是它多一行「属于」、少一块「子商品」。
> 桌面端仍然**保持一列从上往下**，不拆页签 —— 商家自己否掉了页签（"看着很头疼"是排版问题，不是分页问题）。

**桌面端没有"浏览态 / 编辑态"这一说**：抽屉本身就是编辑面（字段失焦即存），再套一层
「编辑」按钮只会让人多按一次、还多一个会忘记复位的状态位。所以桌面端是：
**添加框常驻 + 移出只走右键**。

> 两份前端的形态差在这里是**故意的**：手机没有右键，只能靠一个模式把"能不能左滑"关起来；
> 桌面有右键，右键本身就是"我已确认要对这一行做点什么"的信号，不需要模式。
> 唯一共同点是**移出入口都不常驻**（手机靠左滑、桌面靠右键）—— 一排「移出」按钮已否掉两次。

## 六、可移除性：6 个接入点

商家明确要求"这属于附加功能，哪天不好我可能想去掉"。所以套装的一切改动**只允许出现在这 6 个地方**，每个都带统一标记注释：

```js
// ===== 套装（可整体移除）=====
```

| # | 接入点 | 文件 |
|---|---|---|
| 1 | 画册卡片的「套」角标 + "含 N 件" | `webview/mobile/app.js`、`shopTool/client-product.js` |
| 2 | 筛选面板的「只看套装」开关 | `webview/mobile/app.js` |
| 3 | 详情页套装区块（合计 + 子商品清单 + 添加/移出） | `webview/mobile/index.html` + `app.js`、桌面 `fragment.html` + `client-product.js` |
| 4 | 子商品详情页的「属于 T001」 | 同上 |
| 5 | 新建页的类型开关 | 同上 |
| 6 | 后端：`kind` 读写、`set_items` 增删查、跨类型改号校验、导入拒绝 T 行 | 新文件 `handlers/sets.ts` + `db.ts` 的少量几处 |

**拔掉的步骤**（写在这里，免得将来现推）：

1. 关掉一个开关常量（`SETS_ENABLED=false`）→ 6 个入口全部消失，功能"看不见了"。
2. 想彻底清：`DROP TABLE set_items`；`products.kind` 那一列可以留着不管（`DEFAULT 0`，不碍事），要删列则重建表（SQLite 不支持 `DROP COLUMN` 老版本）。
3. 代码：按 `// ===== 套装（可整体移除）=====` 标记逐个摘，删 `handlers/sets.ts`。

数据上套装就是"一批 `code LIKE 'T%'` 的行 + 一张 `set_items`"，图片夹是 `T001/` 这样的目录，删起来是"删几行 + 删几个目录"，不牵连别的。

## 八、建议的实现顺序

每一步都能单独验证，不要一口气全做完。

1. **数据层**：`kind` 列迁移 + `set_items` 建表 + `db.ts` 的四个接口（增删查）—— 用 SQL 直接验证，界面不动。
2. **后端**：`handlers/sets.ts` 四个消息 + 校验 + 删除连带 + 跨类型改号校验。
3. **手机版详情页**：套装区块（合计 + 清单 + 添加/移出）—— 这是功能的核心，先让它能用。
4. **手机版其余**：画册角标、筛选开关、子商品详情页的「属于」、新建页类型开关、跳转返回。
5. **桌面版**：右键移出 + 详情抽屉 + 新建开关。
6. **导入导出**：拒绝 T 行 + 导出带组成列。
7. **可移除性自检**：全局搜一遍，确认套装代码只在那 6 个位置（`grep -rn "套装" src/ | grep -v "可整体移除"` 的结果应该全是文档/注释）。
